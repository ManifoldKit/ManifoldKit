Section 1

Principles

Every mockup below follows these five rules. They come from the research synthesis: what Apple mandates by September 2026, what ChatGPT/Claude/Gemini converged on, and what the strongest theming architectures (Material 3, Stream Chat, shadcn) share.

Content scrolls under glass

The transcript bleeds edge-to-edge beneath translucent bars. The composer is glass — a floating capsule on iOS, a docked bar on macOS. On pre-26 OSes the same treatment renders in system materials.

Shared components, native chrome

Bubbles, tool cards, reasoning, tokens, and shimmer are identical across platforms. Chrome is not: toolbars, composer placement, picker presentation, and selection follow each platform's own conventions, and pointer/hover feedback is first-class on macOS.

Tokens all the way down

No component references a raw Color. Everything routes through semantic tokens in one ManifoldTheme — swap the semantic layer, re-skin the whole surface. This page is styled from that exact token set.

State is data, styling decides

Streaming, failed, awaiting-approval are typed states on style-protocol Configuration structs. The default styles render them; a consumer's styles may render them any other way.

Quiet until it matters

Live work shimmers (the Apple Intelligence / shadcn convergence); finished work settles into a static badge. Reasoning is collapsed by default with a one-line live preview. No persistent chrome competes with the conversation.

Concentric geometry

Corner radii are derived, not fixed: a nested element's radius = parent radius − padding. One shape scale in the theme replaces today's scattered 4/6/8/12 pt constants.

Section 3

Composer states

The composer is a single field plus at most three affordances: the "+" menu, voice, and send. Every other action (photos, vision, files, tools) lives inside "+". The capsule grows with content; the accessory slot (voice transcription, quick actions) renders above the capsule as its own glass element.

Gating is unchanged — the redesign moves geometry, not seams. Each "+" menu item maps 1:1 to the existing ManifoldConfiguration.Features flag that gates today's button row, and items honor the same capability checks (e.g. supportsImageAttachments). The mic appears only when ComposerPermissionGate passes — a missing NSMicrophoneUsageDescription removes it entirely, exactly as it removes the button today. Voice itself remains an optional ManifoldVoice integration surfaced through the chatComposerAccessory slot, not built-in chrome; the mic glyph in these mockups renders only when that integration (or dictation) is installed and permitted.

Tool invocation lifecycle

One card, four typed states — awaitingApproval → running → completed | failed — delivered to ToolInvocationStyle as configuration data. Status colors come from the theme's semantic tier, not literals (today's hardcoded .orange.opacity(0.15) retires).

Section 5

Model picker — a two-level design

The selection experience is the most option-dense component in the framework: a model row can carry identity, type, quantization, size, a five-tier capability rating, three computed capability flags, a tool-call claim, a vision projector, two distinct kinds of compatibility (backend registered vs. device-RAM fit), five download states, and benchmark results. No single surface should show all of that. The design splits it: a quick switcher (the toolbar-chip popover/palette — answer one question: what do I talk to right now?) and the management sheet (the existing Select / Download / Storage surface — where the full depth lives). The switcher shows identity + one fitness signal + capability glyphs; everything else is progressive disclosure in management.

The one structural change: a unified switcher list. Today local models (ModelRegistry.availableModels) and cloud endpoints (APIEndpointRecord via EndpointStore) are separate, mutually-exclusive flows that are never co-presented — ModelManagementSheet's three tabs never show endpoints. The switcher unifies them into one "everything you can talk to" list. The mutual exclusion already exists in the selection model (selecting a model clears the endpoint and vice versa), so this is a presentation-layer merge plus one registry-level union — but it is new plumbing, and it's the picker redesign's real feature.

The switcher's rules

  1. 1
    One fitness signal per row, qualitative. The dot is device-RAM fit (ModelLoadPlan.canRunModel); backend-registration compatibility renders as a dimmed row with its reason string — the two are different failures and never share an indicator. Raw tok/s and score decimals stay out of the switcher, per the fit-score design rationale.
  2. 2
    Capability glyphs come from data, not marketing. ✦ ⚙ ◎ map to supportsReasoning / toolCallClaim / mmprojURL — already computed on ModelInfo, currently unrendered. A claim is shown as a claim (⚙ is the chat template's word, not a verified capability).
  3. 3
    Live states are visible in place. A downloading model shows progress in its row; a failed endpoint shows its fault and is one tap from the fix (§6A's recoverable-fault pattern). "In use" marks the loaded model; selection ≠ loaded, and the switcher reflects ModelLoadStatus during the load.
  4. 4
    "Thinking budget", not "reasoning effort". There is no effort enum in the framework — the lever is GenerationConfig.maxThinkingTokens (nil = backend default, 0 = off, N = cap). The segmented control maps Off → 0, Auto → nil, Extended → a named budget, and renders only when the loaded model's ModelManifest.supportsThinking is true. Sampler knobs elsewhere gate on supportedSamplingParameters the same way — never show a control the backend won't honor.
  5. 5
    Depth lives in management. "Manage models…" opens the existing sheet: quant variants grouped with "best for your device", fit/speed/curated badges, benchmark runs, import, storage, endpoint editing. The switcher never grows tabs.

Section 6A

Shell & state screens

The states every consumer app passes through — first run, loading, failure — drawn deliberately, because improvised state screens are where SDK-built apps look cheapest. The rule: errors state what happened and what to do next, in the theme's status voice, without stealing the screen — a failed turn never blanks the transcript, a recoverable fault is a banner, and the composer stays live whenever sending could succeed. Structural Form screens (settings, storage, endpoint editor) are deliberately not drawn — their disposition rows in §12 fully specify them.

Section 6B

Connected services (MCP) — promoted into the package

Decision: in scope for Unit 2. The connect / OAuth / consent flow currently exists only in the demo app; the package ships just a tool-count row. That means every MCP consumer rebuilds the same surface — so a themed Connected Services view moves into the package (shipping in ManifoldUIModelManagement's settings family, marked experimental like ManifoldMCP itself: may break in any minor, always migration-noted). The design rules: connection state is a status-tier dot, consent is explicit and shown before first tool exposure, a faulted server carries its fix inline (§6A's pattern, reusing the existing reauthenticate hook), and tool counts surface the Foundation 16-tool cap honestly.

The enforcement rule (this repo's culture): an audit test — HardcodedColorAuditTest with an in-file test_sabotage_ — fails CI when view code references a raw status/theme color outside the theme definition files. Section 8

Style-protocol map

MessageBubbleStyle proved the pattern (Apple's ButtonStyle idiom: a protocol with a data-only Configuration, resolved via environment). The refresh extends it to every surface a consumer will want to re-skin, and adds one new seam: a part-level renderer, so a host can replace just tool cards without rebuilding whole messages.

Section 9

OS fallback matrix

The package floor stays iOS 18 / macOS 15. Glass is progressive enhancement behind #available(iOS 26, macOS 26, *). On iOS the fallback is a system material with identical geometry. On macOS the chrome is system-owned, so the fallback is graceful rather than identical — the window toolbar and sidebar render in whatever the OS provides, and there is no pre-26 equivalent of backgroundExtensionEffect. Standard glass APIs inherit the OS-level glass-intensity setting WWDC26 introduced, for free.

Section 11

What the test suite should pin

  • Default-appearance characterization — two anchors: during the token refactor (phase 1), resolved values equal today's shipped appearance byte-for-byte; after the defaults flip, the suite pins the new defaults and separately pins that .classic reproduces the pre-refresh appearance.
  • Token plumbing — a custom ManifoldTheme injected at the root resolves through every consuming surface: composer, tool cards, thinking, citations, sidebar, model-management badges. One assertion per surface.
  • Style-protocol dispatch — a custom style installed via each new modifier receives correct Configuration data for every typed state (tool lifecycle ×4, composer phase ×4, thinking ×2).
  • Part-renderer fallthrough — overriding one part kind leaves all other kinds rendering via defaultPartView().
  • HardcodedColorAuditTest — plus its in-file sabotage test, registered with AuditSabotageCoverageAuditTest.
  • Availability seams — glass paths compile under the 26 SDK and fall back below it; snapshot or build-matrix coverage for both branches (macOS 15 CI runner exercises the fallback naturally).
  • Accessibility invariants — Reduce Motion disables shimmer/spin; Dynamic Type scaling of the shape/type scale; VoiceOver labels on tool-state badges and the send/stop toggle.
Shipping shape (revised after review, reconciled with the no-phased-splits rule): Unit 1 — token refactor. Its own PR: pure internal rewiring, zero visual change, characterization tests lock today's appearance. Independently valuable regardless of the redesign. Unit 2 — the visual overhaul. Glass chrome, new default styles, style protocols + part renderer, composer/picker redesign, and the classic presets are one feature — built as a stacked draft series and merged as a single unit so no intermediate CI-triggering PR ships a half-flipped default. Classic presets land in the same unit so the migration path exists the moment defaults change. Docs and tests ship inside each unit, not as follow-ups.

Three dispositions: Redesigned (specified above with mockups), Token restyle (no mockup needed — the element keeps its structure and inherits ManifoldTheme: semantic colors, shape scale, glass/material surfaces; treatment noted where it isn't obvious), and Diagnostic-exempt (developer-facing; function over form, allowlisted in the color audit).
