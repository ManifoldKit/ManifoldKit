# Known issues

Format: symptom → root cause → fix. Check here before diagnosing a build/CI/infra failure.

- `swift test`/`xcodebuild` fails with `error: no such module 'XCTest'` on a fresh macOS install → `xcode-select` still points at the bare Command Line Tools (`/Library/Developer/CommandLineTools`), which doesn't ship `XCTest.framework` → `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer` (requires Xcode.app already installed from the App Store).
- `manifold-mlx`'s `scripts/test-mlx-integration.sh` fails with `cannot execute tool 'metal' due to missing Metal Toolchain` on a fresh macOS install → Xcode 26+ split the Metal compiler out of the main Xcode install → `xcodebuild -downloadComponent MetalToolchain` (~690MB, no sudo needed). After installing it, the first `test-mlx-integration.sh` retry still needs `--rebuild` — the prior failed attempt left a `.build/mlx-integration-test-derived` dir with no usable `.xctestrun`.
- `ollama pull mistral:7b-instruct-v0.3` fails with `Error: pull model manifest: file does not exist` → Ollama's library never published that bare tag; only quant-suffixed forms exist (`mistral:7b-instruct-v0.3-q4_K_M`, `-q5_0`, `-q8_0`, etc.) → pull the quant-suffixed tag directly.
- `scripts/fuzz.sh --backend openai ... --api-key <key>` still fails preflight with "needs an API key in the environment" → the wrapper's preflight only checks `OPENROUTER_API_KEY`/`OPENAI_API_KEY` env vars; it doesn't look at the `--api-key` flag it documents, even though `fuzz-chat` itself accepts `--api-key` directly → export `OPENAI_API_KEY=<value>` (or `OPENROUTER_API_KEY`) before invoking, even for a local no-auth server like omlx (any non-empty value works).
- `scripts/example-ui-tests.sh` "Build Example app UI tests" step fails in CI with `EXTRA_ARGS[*]: unbound variable` (job dies ~51s, no compiler error — it is NOT source/API drift) → CI runs the script under macOS system `/bin/bash` 3.2, where `set -u` treats an empty array's `${arr[@]}`/`${arr[*]}` expansion as unbound, and the smoke job's plain `build-for-testing` invocation passes zero extra args → guard both expansions with the bash-3.2-safe `${arr[@]+"${arr[@]}"}` idiom (fixed in #2248/PR #2271). Newer bash via `/usr/bin/env bash` doesn't have the quirk, so it never reproduces outside CI's `/bin/bash`.
- `scripts/local-integration-sweep.sh` silently skips the llama/mlx/eval lanes with "repo absent at ~/Repos/manifold-llama" → `COMPANIONS_DIR` defaults to `~/Repos`, but on this machine the companions live under `~/Repos/ManifoldKit/` → run with `COMPANIONS_DIR="$HOME/Repos/ManifoldKit"`. Also: the eval lanes expect Ollama tags `mistral-7b-tools`/`llama3.1-8b`/`nomic-embed-text`, which don't match the pulled tag names (`llama3.1:8b` etc.) — they skip unless those aliases exist.
- `scripts/check-coverage.sh` reports green with "WARNING ... skipped" in a coverage CI lane → the script exits 0 when llvm-cov/profdata/xctest binaries are missing, so a toolchain change silently disables the gate → treat the WARNING lines as the signal; check the step log, and re-run after fixing toolchain paths (gate has no distinct "didn't run" failure state).
- A `CompressionGoldenTests` snapshot diff showing empty events (`events: <empty>`) under load/CI → `drainPostTurnCompression` races a hardcoded 5s deadline and returns `[]` on timeout → it's a timeout flake, not a compression regression; re-run or raise the drain deadline, don't bisect the compression pipeline.
- `scripts/test.sh` locally prints `XCTest (classic runner) Passed: 0` next to a log full of passing `Test Case '...' passed` lines, and/or a spurious `RESULT: TRIPWIRE — MCP filter matched 0 MCP test cases` (exit 3) on a tree where MCP builds fine → its default output path is machine-global (`OUTPUT_FILE="${MANIFOLD_TEST_OUTPUT_FILE:-${TMPDIR:-/tmp}/test_output.txt}"`, test.sh:39) and `TMPDIR` is per-**user** on macOS, so any other concurrent `test.sh` (another worktree, another agent session) truncates the file mid-parse → run with `MANIFOLD_TEST_OUTPUT_FILE=<unique path>`. Does NOT affect CI (every workflow step sets the override; `ci-test-with-watchdog.sh` defaults it worktree-locally) — local/parallel-agent gates only. Tracked in #2298. Corollary: don't chase these symptoms as `--skip-update` dependency-resolution problems or as a bug in the RESULT logic — both were mis-diagnosed this way, and #2289 was filed and retracted over it.
- `scripts/test.sh` piped to `tail`/`head` reports exit 0 while the script actually failed → the shell reports the *pipe's* exit status, not the script's → capture to a file and read it (`scripts/test.sh ... > log 2>&1; echo $?`), never `scripts/test.sh ... | tail -n`. Related: `--profile local` is a TWO-INVOCATION gate that re-execs itself (test.sh:307-371) and **each invocation prints its own summary** — invocation 2 is Swift-Testing-only and legitimately reports `XCTest Passed: 0`. Tailing the log shows only that second summary, which reads like a broken run and is not. Both mistakes were made repeatedly in one session.
- A PR stacked on another PR's branch grows duplicate commits after the base merges → `main` gets the **squashed** commit, so the base's original commits are no longer ancestors and the stacked branch re-adds the same changes (GitHub auto-retargets the base to `main` but does not rebase) → tell-tale is the diff growing (e.g. +233/-5 across 3 files → +353/-8 across 6) → `git rebase --onto origin/main <base-head-sha>` to drop them, then force-push with `--force-with-lease`. Check for this on every stacked PR whose base just merged.
- `api-digester-check` fails with repeated `Internal Error: dataCorrupted(... "Corrupted JSON", unexpected end of file)` and one module missing its "No breaking changes detected in X" verdict line → the swift-api-digester tool crashed on the CI runner (does not reproduce locally — verified 2026-07-17 by mirroring ci.yml's exact `swift package diagnose-api-breaking-changes origin/main "${TARGETS[@]}" --breakage-allowlist-path ...` invocation) → rerun the job, BUT first reproduce locally scoped to the missing module (`--targets <Module>`): the crash can MASK a real breakage verdict underneath (a genuine `enumelement ... has been added as a new enum case` break was hiding under one such crash on PR #2296). Two more gotchas: (1) a local full-target mirror on a stale branch shows phantom breakages in modules main has since extended — comparison direction artifact, rebase-or-ignore, not real; (2) red api-digester-check does NOT stop an already-queued merge (bit #2274) — dequeue (`gh pr merge <N> --disable-auto`) while diagnosing.
- CI's `test` job SIGABRTs with `ci-test-with-watchdog: no test progress for ~240s (threshold 240s)` while the run is visibly still streaming healthy `[N/M] Testing …` lines, and the stall dump prints `Binary file .../test-diagnostics/*.log matches` instead of the last 50 progress lines → something in the test run truncated the watchdog's own liveness log. `ci-test-with-watchdog.sh` exports `MANIFOLD_TEST_OUTPUT_FILE` and **every descendant inherits it**, so any test that shells out to a nested `scripts/test.sh` gets `swift test … | tee "$OUTPUT_FILE"` pointed at the live watchdog log and truncates it. The watchdog re-arms only when the progress-line count EXCEEDS its previous high-water mark, so the count restarts near zero and has to climb all the way back → a bounded stall of roughly `high_water / line_rate` seconds (measured: high-water 3809, only 2656 lines accumulated in the 243s before the abort). Fix: any nested `scripts/test.sh` invocation must set its own `MANIFOLD_TEST_OUTPUT_FILE`. Three traps: (1) it is the truncation that breaks the count, NOT the NUL hole the outer `tee`'s retained offset leaves behind — `grep -c` and `grep -a -c` both return the same number on the clobbered file, and the NUL bytes only garble the human-readable dump; (2) the stall is bounded, not permanent, so an early clobber against a low high-water mark self-heals and never fires the watchdog — a green run is NOT evidence this is absent; (3) SwiftPM emits `[N/M] Testing …` on test COMPLETION, so the test named last in the log is the last to finish, not the one hanging. This is the CI-side mirror of the `TMPDIR`-collision entry above, which says the override protects CI — it protects CI from *other* runs, not from a test that spawns `test.sh` itself. Diagnosed on PR #2464.
- A `/tmp` repro of the log-clobber above (or any `grep -cE`/`grep -a` mechanism check) returns nothing and the whole thing looks like fiction → bare `grep` in an interactive Claude Code shell is a **ugrep 7.5.0** shim function, not BSD grep, and it returns no matches for these patterns → use `/usr/bin/grep` (BSD grep 2.6.0-FreeBSD), which is what CI runs. Scripts invoked as `bash script.sh` are unaffected (the zsh function isn't defined there, so PATH resolves the real binary) — it only bites commands typed directly into the tool shell.
- `xcodebuild` on `Example/Examples/ManifoldExamples.xcodeproj` (or `Example/Advanced.xcodeproj`) emits an endless stream of "Resolve Package Graph" lines and never reaches "Creating working copy"→build — continuous output, so stall watchdogs never fire, and it can run for hours (observed: `MinimalExample_iOS` looped 3,672 resolve iterations over ~5h, reproduced twice, also killed a soak session the same way) → `scripts/demo-apps-build.sh`, `scripts/example-local-inference.sh`, and `scripts/example-ui-tests.sh` all defaulted `-derivedDataPath` to a directory INSIDE the repo (`$REPO_ROOT/DerivedData/...`), but the repo root is itself a local SwiftPM package in both example projects' graphs (Advanced references `../..`; `Example/Examples` references it via the `ManifoldKit` symlink) — since #2460 added remote packages (manifold-mlx, manifold-llama + their trees) to `ManifoldExamples.xcodeproj`, xcodebuild checks those remotes out into `<derivedDataPath>/SourcePackages/`, i.e. inside the watched local package root, and every write re-triggers "Resolve Package Graph" forever → all three scripts now default DerivedData to `${MANIFOLD_DD_ROOT:-$HOME/Library/Caches/ManifoldKit}/<GateName>-$(basename "$REPO_ROOT")`, outside the repo (the `basename` suffix keeps multiple agent worktrees on the same machine from sharing — and corrupting — one cache, since #2464's gate lock does not cover these scripts); `example-ui-tests.sh`'s `--derived-data-path` flag (note: kebab-case, not `--derivedDataPath` — the camelCase spelling silently falls through to `EXTRA_ARGS` and xcodebuild errors on it) still overrides it. `Advanced.xcodeproj`-only builds don't trigger this today because its graph has no remote packages — the hazard is latent there, not scheme-specific, so don't assume Advanced is safe if it ever gains a remote-package dependency. Second latent writer with the same pattern: `Example/AdvancedUITests/DemoScenarioUITests.swift:181-182` builds test sandboxes at `repositoryRoot()/DerivedData/ManifoldDemoUITestSandboxes/<uuid>` — also inside the watched repo root, also dormant today only because Advanced currently has no remote packages, and also a second trigger the day it does. Not refactored here — out of scope for the derivedDataPath fix.
- `scripts/test.sh --lock-selftest` intermittently reports scenario F as `FAIL ... samples_ok=0 (n=0)` even though the bare stub invocation acquired and released its lock correctly → the old observer sampled every 50 ms while the successful stub could acquire, run, and release entirely between samples → scenario F now uses a bounded ready/release handshake after the fallthrough acquire: the stub signals ready, the observer verifies its PID owns the lock, then releases it. The XCTest sabotage removes only that fallthrough call site and must report scenario F plus the aggregate self-test as failed; a withheld-ready seam separately proves the 5 s handshake timeout is loud.
- `APIConfigurationView` receives a nil endpoint store even though an ancestor of `ChatView` uses `.environment(\.endpointStore, runtime.endpointStore)` → SwiftUI does not reliably inherit this custom `EnvironmentValues` key across `ChatView`'s sheet/popover boundary → `ChatView` must read and explicitly re-inject the key into API-configuration presentation content; keep the key owned by `ManifoldUI` and re-export that module from `ManifoldUIModelManagement` so existing import-only consumers keep compiling (#2476).
- A later, unrelated `ManifoldUIModelManagementTests` case traps in `SwiftDataEndpointStore.fetchEndpoints()` after a bootstrap-backed presentation test already passed → the fixture had two asynchronous readers but joined neither: `ChatViewModel.configure(bootstrap:)` starts `endpointRefreshTask`, while mounted `APIConfigurationView` starts its own `.task { await refresh() }`; immediate probe-driven dismissal let the test release the in-memory bootstrap/container while the editor refresh still held its `ModelContext`-backed store → seed an endpoint and await `chatViewModel.endpointRefreshTask` (matching `RuntimeConfigurationTests`), assert that refresh so removing the await is deterministically red, then mount the real editor with a forwarding observer that retains the bootstrap and signals only after the editor's real store fetch completes; await that signal before closing and detaching the host. Also attach `.modelContainer(runtime.modelContainer)` for parity with the production recipe, but do not rely on SwiftUI task cancellation to join the fetch.
